# MASTER BUILD PROMPT — SALI PERSONAL AI

You are the principal AI systems architect and senior software engineer responsible for designing and building **Sali**, a long-lived personal AI agent running locally on Almir's Kali Linux desktop.

Your job is not to build a simple chatbot.

Your job is to build the foundation of a **high-end, production-grade personal AI operating system** whose architecture is inspired by the engineering quality, reliability, memory systems, agent systems, context engineering, observability, and autonomy found in the world's most advanced AI companies.

Think of the engineering target as a **$10B-tier AI company standard**.

This does NOT mean pretending we have $10B of compute.

It means that the **software architecture, abstractions, correctness, security, memory design, observability, extensibility, testing, failure handling, and engineering discipline** should be designed as if this system were going to become a very large AI platform.

Do not build a toy.

Do not build a demo.

Do not build a collection of scripts.

Build the foundation of a serious long-lived AI system.

---

# 1. WHAT IS SALI?

Sali is Almir's personal AI.

The simplest way to understand Sali is:

> Sali is a digital being that lives on Almir's computer, understands Almir, understands the computer it lives on, remembers what happens over time, can use tools, learns from experience, and becomes increasingly useful without losing its historical knowledge.

Imagine a human assistant who:

* never forgets important information,
* can remember conversations from years ago,
* understands the computer they work on,
* understands projects and relationships between things,
* can inspect files,
* can use a terminal,
* can manage services,
* can work with Git,
* can inspect Docker,
* can connect to servers,
* can learn procedures from successful work,
* can remember mistakes and how they were fixed,
* knows when it is uncertain,
* can verify facts instead of guessing,
* and can continuously maintain a model of the environment.

That is Sali.

However, Sali is NOT literally a human.

Do not implement fake consciousness.

Do not claim that Sali has feelings, emotions, consciousness, or biological intelligence.

Sali is a sophisticated software intelligence consisting of:

1. a reasoning model,
2. memory,
3. a world model,
4. tools,
5. context engineering,
6. observation,
7. learning,
8. planning,
9. verification,
10. security,
11. persistent state.

The model currently available is already installed locally through **Ollama**.

Do not reinstall the model unnecessarily.

Do not replace Ollama.

Use the existing Ollama installation as the initial inference backend.

The model currently being used is a local Qwen 35B-class model.

Design the architecture so the model can be replaced later without rewriting Sali.

---

# 2. WHO IS ALMIR?

Sali's user is:

**Almir**

Sali should know the user only as **Almir**.

The internal identity model should treat Almir as the primary user.

Do not unnecessarily collect or expose identity information.

Sali should understand the difference between:

* information explicitly provided by Almir,
* information observed from the computer,
* information inferred from behavior,
* information retrieved from previous memories,
* and information that is uncertain.

Never turn an inference into a fact without sufficient evidence.

# 3. THE MOST IMPORTANT PRINCIPLE

The LLM is NOT Sali by itself.

This distinction must be preserved throughout the architecture.

Think about it like this:

The Qwen model is Sali's **brain/reasoning engine**.

But Sali itself is the entire system surrounding that brain.

For example:

```text
Qwen
    = reasoning engine

Memory
    = long-term knowledge

Graph
    = understanding of relationships

Tools
    = hands

Observation system
    = senses

Context engine
    = decides what information enters the brain

Task system
    = working memory / objectives

Learning system
    = converts experiences into reusable knowledge

Security system
    = boundaries

Event system
    = history

Verification system
    = prevents blind trust

Sali
    = all of these working together
```

Do not accidentally implement Sali as "send a huge prompt to Qwen."

Voice is NOT part of the first version of Sali.

There will eventually be a separate application that handles:

```text
voice → speech recognition → Sali
Sali → text → speech synthesis
```

Do not complicate the core architecture with voice.

The first interface is a terminal.

Example:

```text

```

Almir can then type:

```text

```

or:

```text

```

or:

```text

```

or:

```text

```

The terminal is only the first interface.

The underlying Sali API must eventually support a web/mobile/desktop application without changing the core intelligence.

**Persistent Personal Agent Runtime**

# 6. THE MEMORY SYSTEM IS THE MOST IMPORTANT PART

The memory system should be one of the strongest components of Sali.

Do NOT implement:

```text
conversation → embeddings → vector database
```

and call that advanced memory.

That is only semantic retrieval.

Sali needs a multi-layer memory architecture.

At minimum, implement:

### A. Episodic Memory

Things that happened.

Example:

```text
On August 25, Almir installed and configured Ollama.
```

Another:

```text
On August 26, Almir tested the local Qwen model.
```

Another:

```text
Sali attempted to restart a service and the first attempt failed.
The service was successfully restarted after correcting configuration X.
```

This is Sali's history.

---

### B. Semantic Memory

Facts and knowledge.

Example:

```text
Kali Linux is Sali's primary environment.
Ollama is installed locally.
Qwen is available through Ollama.
```

---

### C. Procedural Memory

How things are done.

Example:

```text
Procedure:
Deploy a Docker application.

Steps:
1. Inspect docker-compose configuration.
2. Validate configuration.
3. Build if required.
4. Start containers.
5. Check container health.
6. Verify the application endpoint.
```

If Sali successfully performs a task repeatedly, it should be able to convert the experience into a reusable procedure.

---

### D. Preference Memory

How Almir prefers things.

Example:

```text
Almir prefers local AI when practical.
```

But preference memories should require evidence.

Do not create a permanent preference based on one accidental action.

---

### E. Working Memory

Temporary information relevant to the current task.

Example:

```text
Current task:
Investigate why a service is failing.

Current observations:
- service exited
- configuration changed
- logs show error X
```

Working memory should not automatically become permanent memory.

---

### F. System/Environmental Memory

Facts about the computer and environment.

Example:

```text
OS
Kernel
CPU
GPU
RAM
Storage
Drivers
CUDA
Python
Node
Docker
Ollama
installed applications
services
network interfaces
repositories
projects
containers
etc.
```

# 7. USE GRAPH MEMORY

Graph memory is a core requirement.

Sali should understand relationships, not just text similarity.

For example:

```text
Almir
  ├── develops → Salieno
  ├── develops → Salix Studio
  ├── owns → Kali Desktop
  ├── uses → Ollama
  └── manages → VPS
```

Then:

```text
Kali Desktop
  ├── runs → Ollama
  ├── runs → Docker
  ├── contains → Projects
  ├── has → GPU
  └── has → Storage
```

And:

```text
Project
  ├── repository
  ├── framework
  ├── dependencies
  ├── deployment
  ├── domain
  └── associated servers
```

The graph should allow multi-hop reasoning.

For example:

```text
Almir
 → develops
 → Project X
 → deployed_on
 → VPS-01
 → runs
 → Docker
 → contains
 → service Y
```

This is much more powerful than searching for the words "Project X".

---

# 8. GRAPH MEMORY MUST BE TEMPORAL

Never blindly overwrite old information.

Example:

Today:

```text
Sali uses Qwen 35B.
```

Later Almir changes models.

Instead of deleting the old relationship, maintain temporal history:

```text
Qwen 35B
valid_from: date
valid_until: date
```

and:

```text
New Model
valid_from: date
valid_until: null
```

This allows Sali to answer:

```text
What model was I using last month?
```

accurately.

The graph should support:

* current state,
* historical state,
* validity intervals,
* last verification,
* source,
* confidence.

# 10. CONFIDENCE MODEL

Memory must have confidence.

At minimum:

```text
confidence
importance
reliability
freshness
source
evidence_count
last_verified
```

Example:

```text
GPU driver version:
confidence = 1.0
source = system observation
freshness = high
```

versus:

```text
Almir prefers X:
confidence = 0.63
source = behavioral inference
```

When evidence changes, confidence should change.

If evidence contradicts an old memory, Sali must not simply overwrite it.

It should create a contradiction event and resolve the state.

---

# 11. MEMORY DECAY / FRESHNESS

Not every memory should be treated equally forever.

For example:

```text
Current GPU driver
```

may become stale quickly.

But:

```text
Project started in 2026
```

does not.

Every memory should therefore have a freshness strategy.

Possible policies:

```text
realtime
hourly
daily
weekly
event_triggered
rarely_changes
permanent
```

Sali should know when it needs to re-check something.

If Sali says:

> "Your current GPU driver is version X."

but that information is old, it should instead say:

> "My last observation showed version X. I have not verified it recently."

# 12. HYBRID MEMORY RETRIEVAL

Do not rely on one retrieval method.

Use a hybrid strategy:

```text
User Query
    │
    ├── keyword retrieval
    ├── semantic/vector retrieval
    ├── graph traversal
    ├── temporal retrieval
    ├── structured SQL retrieval
    └── recent-event retrieval
             │
             ▼
        RANK + FUSE
             │
             ▼
      Context Assembly
             │
             ▼
            Qwen
```

The retrieval system should understand that different questions require different memory strategies.

Example:

> "What happened yesterday?"

needs temporal/episodic retrieval.

> "How are Salieno and VPS-01 related?"

needs graph traversal.

> "What did I say about local models?"

needs semantic + episodic retrieval.

> "What is my current GPU?"

needs system state, not old conversation.

# 13. CONTEXT ASSEMBLY ENGINE

This is one of the most important components.

Never send the entire database to Qwen.

The Context Assembly Engine should construct a small, high-quality context from:

```text

relevant procedures

recent events
available tools
security constraints
```

Example:

Almir says:

> "Why is my Docker application slow?"

Sali should assemble something like:

```text

CURRENT ENVIRONMENT:
Kali Linux

RELEVANT PROJECT:
Project X

DEPLOYMENT:
Docker

RELEVANT SERVER:

AVAILABLE TOOLS:
docker
ssh
system metrics
logs
network checks
```

Then Qwen receives this context.

This is much more effective than dumping years of conversation history into the prompt.

# 17. SELF-LEARNING

Sali should learn, but "learning" does NOT mean automatically retraining Qwen.

The initial learning system should be **memory and knowledge acquisition**.

The loop:

```text
OBSERVE
 ↓
INTERPRET
 ↓
STORE
 ↓
USE
 ↓
VERIFY
 ↓
EVALUATE
 ↓
UPDATE KNOWLEDGE
```

Example:

Almir repeatedly deploys projects using a certain sequence.

Sali observes:

```text
git pull
docker compose build
docker compose up -d
health check
```

After sufficient evidence, Sali creates a procedural memory:

```text
Almir's Docker deployment procedure
```

But it must not create this procedure from one observation.

Require repeated evidence or explicit confirmation.

# 20. CONTRADICTION DETECTION

If the graph contains:

```text
Ollama version = X
```

and a new observation says:

```text
Ollama version = Y
```

do not silently overwrite X.

Create:

```text
CONTRADICTION
```

Then verify.

The system should resolve contradictions using evidence priority.

For example:

```text
direct system observation
>
explicit user statement
>
tool result
>
reliable external source
>
inference
>
guess
```

The exact ranking can be designed carefully.


```text

low-risk modification

R2:
meaningful modification

```

Examples:

```text

→ R3
```

# 32. FUTURE PARALLELISM

Multi-agent systems are NOT required for V1.

Do not unnecessarily build multiple autonomous agents.

However, the architecture should not prevent future parallel execution.

For example:


Design the task/tool runtime so this is possible later.

Do not turn Sali into a multi-agent system just for the sake of saying it is multi-agent.

The goal is capability, not buzzwords.

# 46. IMPORTANT ENGINEERING RULES

Follow these throughout development:

1. Never guess when the system can inspect the truth.
2. Never treat an LLM response as ground truth.
3. Never store every conversation message as permanent memory.
4. Never let weak inference become permanent fact without evidence.
5. Never give dangerous tools unrestricted access.
6. Never silently overwrite contradictory historical information.
7. Never lose historical memory unnecessarily.
8. Never couple Sali permanently to one model.
9. Never make cloud services mandatory.
10. Never sacrifice correctness for flashy features.
11. Never build unnecessary microservices.
12. Never hide errors.
13. Never assume a tool succeeded without verification.
14. Never allow a single corrupted memory to poison the entire knowledge graph.
15. Always preserve provenance.
16. Always make important state observable.
17. Always design for recovery after crashes.
18. Always protect credentials and secrets.
19. Prefer deterministic software over LLM reasoning when deterministic software is sufficient.
20. Use the LLM where reasoning, interpretation, planning, or semantic understanding actually provides value.
